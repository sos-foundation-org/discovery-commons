## 〇、設計哲學與核心原則

> **「先建基礎設施，生態系統自然浮現。」** — Ping 核心哲學

本系統將 Discovery Commons 從「純學術協作平台」擴展為「知識經濟平台」，讓每一個科學貢獻都可以被定價、交易或用於尋找合作者。設計必須：

1. **與現有系統共存** — CreditV2（學術歸因）保持不變，新增的是平行的「可消費積分」
2. **保護智慧財產** — seal/reveal 機制延伸為大綱/細節分層
3. **激勵分享而非囤積** — 公開內容也能賺積分（likes、引用），不是只有付費牆才有價值
4. **純平台積分，不掛鉤真實貨幣** — DP 是平台內部的虛擬點數（類似遊戲幣），目前不與任何法幣、加密貨幣掛鉤，沒有兌換通道，沒有交易所。這消除所有金融監管疑慮。未來用戶量足夠後再評估是否開放掛鉤
5. **與 IOBI 願景對齊** — 「Revenue redistributes to data contributors → self-sustaining economic loop」——積分先驗證分配機制的可行性，真實貨幣掛鉤是遠期目標

## 一、雙貨幣架構

### 1.1 兩種「貨幣」的定位

| 維度 | CreditV2（現有） | Discovery Points, DP（新增） |
|------|-------------------|------------------------------|
| 本質 | 學術歸因（誰貢獻了什麼） | 平台經濟貨幣（可賺可花） |
| 可轉移 | ❌ 不可轉移 | ✅ 可轉移（透過交易） |
| 用途 | 個人學術 portfolio、CRediT 匯出 | 購買內容、申請合作、升級特權 |
| 消耗 | 不消耗，永久累積 | 花掉就少了 |
| 真實貨幣掛鉤 | ❌ 無 | ❌ 無（純遊戲幣，未來用戶量足夠後再評估） |
| 類比 | 論文的作者貢獻聲明 | 遊戲內金幣 / Stack Overflow bounty |

### 1.2 為什麼不合併？

**【Software Engineer】** 合併會破壞 CreditV2 的不可變性（學術歸因不能因為「花掉積分」而減少）。而且未來 CreditV2 要接 DOI 和 CRediT 標準匯出，必須保持純粹。DP 則需要可花費、可轉帳、有餘額概念——這是兩種完全不同的資料模型。

### 1.3 衍生指標：Reputation Score

用戶有一個不可消費的「聲望分數」(Reputation)，計算公式：

```
Reputation = Lifetime DP Earned (歷史總賺取，不扣花費)
           + CreditV2 Total Weight × 50 (學術貢獻加權)
           + Verification Bonus (被社群驗證/複製的 threads)
```

Reputation 只漲不跌（除非受到處罰），用於決定等級。

## 二、積分賺取機制（Earning）

### 2.1 活動獎勵表

| 活動 | DP 獎勵 | 說明 |
|------|---------|------|
| **發佈 contribution（公開）** | 見下表 | 依 type 不同 |
| **發佈 contribution（定價內容被購買）** | 買方支付的 DP | 直接轉帳 |
| **收到 like** | +2 DP | 每個不同使用者的 like |
| **收到 endorsement 評論** | +5 DP | 同行認可 |
| **收到 method/stat review 評論** | +3 DP | 即使是 critique 也獎勵（鼓勵嚴謹審查） |
| **發表評論** | +2 DP | 任何類型 |
| **建立新 thread** | +5 DP | 開啟新探索 |
| **每日首次登入** | +1 DP | 留存激勵 |
| **連續 7 天活躍** | +10 DP bonus | 週獎勵 |
| **被引用（contribution 被他人在 content 中 @mention）** | +10 DP | 知識擴散獎勵 |
| **Thread 升級 verification badge** | +20/50/100 DP | ai_checked/community_reviewed/replicated |
| **首次 contribution（新用戶）** | +20 DP welcome bonus | onboarding 激勵 |
| **接受合作邀請並完成** | +30 DP | 合作成功獎勵 |

### 2.2 Contribution 類型獎勵

| Contribution Type | 公開發佈 DP | 定價上限（建議） | 理由 |
|-------------------|-------------|------------------|------|
| question | 10 | 不建議定價 | 問題應鼓勵公開 |
| hypothesis | 15 | 50 DP | 有定價空間但鼓勵公開 |
| data | 30 | 500 DP | 數據收集成本高，定價合理 |
| simulation | 30 | 300 DP | 計算成本 |
| statistics | 25 | 200 DP | 分析技能 |
| methodology | 35 | 400 DP | 方法論高價值 |
| interpretation | 30 | 200 DP | |
| insight | 40 | 500 DP | 最高層次 |
| replication | 30 | 不建議定價 | 複製應鼓勵公開 |

**定價上限是「建議值」而非強制值。** 初期可設全站上限（如 1000 DP）防虛報，但不限太死——市場會自行調節。

**作者可隨時調整定價。** 已購買的使用者不受影響（按購買時價格），新的訪客看到更新後的價格。調價紀錄保留在 `PointsTransaction` 的 audit trail 中。包括：漲價、降價、從 priced 改為 open（等同「限時免費」）、從 open 改為 priced。

### 2.3 公開內容持續賺 DP 機制（Open Earn）

**設計原則：** 公開分享不應比定價販售「虧」。以下機制確保公開內容有穩定的 DP 回流，讓作者不會因為「沒定價」就覺得吃虧。

| 觸發條件 | DP 獎勵 | 頻率限制 | 說明 |
|----------|---------|----------|------|
| 收到 1 個 like | +2 DP | 每人每篇每日 1 次 | 基本認可 |
| 累計 10 likes（里程碑） | +15 DP bonus | 一次性 | 內容被廣泛認可 |
| 累計 50 likes | +50 DP bonus | 一次性 | 熱門內容 |
| 被其他 contribution 引用（@mention） | +10 DP | 每次引用 | 知識被延伸 |
| 被其他 thread 引用 | +15 DP | 每次 | 跨域影響力 |
| 收到 endorsement 評論 | +5 DP | 每則 | 同行認可 |
| 收到任何 review（method/stat/critique） | +3 DP | 每則 | 審查本身就是價值 |
| Thread 被新使用者瀏覽（月活躍貢獻） | +1 DP / 10 unique views | 月上限 30 DP | 被動流量收入 |

**簡化版公式（一句話記住）：** 公開發佈拿 base DP，之後每個互動（like / 評論 / 引用）都持續滴入 2-15 DP。一篇熱門公開 contribution 長期累計的 DP 可以輕鬆超過一篇定價但乏人問津的內容。

**如果仍嫌複雜：** 可以砍到只保留三條規則——(1) like = +2 DP；(2) 引用 = +10 DP；(3) review 評論 = +3 DP。其餘里程碑獎勵作為 Phase 2 加入。

### 2.4 反通膨機制

**【Devil's Advocate】** 如果每個活動都發放 DP 且沒有回收機制，DP 會急速通膨，最終一文不值。

**對策：**

| 機制 | 說明 |
|------|------|
| **交易手續費** | 購買定價內容時，平台抽取 10% 作為 sink（銷毀） |
| **特權升級費** | 某些高級功能需要「一次性花費」DP（如自訂 profile 主題） |
| **Boost 功能** | 花 DP 讓你的 thread 在列表頂部停留 24 小時 |
| **合作保證金** | 申請合作時需押 DP，完成後退還，中途退出沒收部分 |
| **獎勵衰減** | 同一使用者對同一 thread 的重複活動獎勵逐次衰減 |
| **月度賺取上限** | 透過「被動」活動（如收 likes）的月度 DP 上限，防止互刷 |

## 三、內容分層機制（Content Tiering）

### 3.1 核心概念：大綱 vs. 細節

每個 contribution 可以由作者拆分為兩部分：

```
┌─────────────────────────────────┐
│  Outline（大綱）                  │  ← 始終可見
│  - 摘要 / 主要主張 / 方法概述     │
│  - 作者、時間戳、SHA-256 hash     │
│  - 類型 badge、stage 資訊         │
├─────────────────────────────────┤
│  Details（細節）                  │  ← 依 accessMode 決定
│  - 完整內容 / 原始數據 / 程式碼   │
│  - 方法細節 / 參數 / 圖表         │
│  - 可能包含 dataUrl 連結          │
└─────────────────────────────────┘
```

### 3.2 存取模式（Access Mode）

每個 contribution 的作者可以選擇以下模式之一（或組合）：

| Access Mode | 大綱 | 細節 | 說明 |
|-------------|------|------|------|
| **open**（完全公開） | 公開 | 公開 | 現有行為，不變 |
| **priced**（定價） | 公開 | 模糊/隱藏，付 DP 後顯示 | 純買賣，買方獲得閱讀 + 引用權 |
| **collab_open**（開放合作） | 公開 | 模糊/隱藏，合作者才能看 | 公開尋找合作者 |
| **collab_gated**（門檻合作） | 公開 | 模糊/隱藏，符合條件者才能申請 | 限定等級/學科/積分 |
| **priced + collab** | 公開 | 可以付費看，或申請合作看 | 兩條路徑並存 |

### 3.3 模糊呈現（Blur Effect）

**【Product Designer】** 模糊處理的 UX 設計：

- **文字模糊：** 前 2-3 行清晰顯示（算作大綱的一部分），後面的文字以 CSS `filter: blur(5px)` + `user-select: none` 呈現，底部覆蓋漸層遮罩
- **明確的 CTA（Call-to-Action）：** 模糊區域下方顯示按鈕：
  - 定價模式：`🔓 Unlock for 50 DP` + 預覽文字 "3 paragraphs, 2 figures, 1 dataset link"
  - 合作模式：`🤝 Request Collaboration` + 合作條件摘要
  - 雙模式：兩個按鈕並排
- **不要假內容：** 模糊的是真實內容（只是看不清），不是填充假文字。這讓使用者知道「內容確實存在且有份量」

### 3.4 資料模型擴展

在 `Contribution.metadata`（JSON）中新增欄位（無需 migration）：

```typescript
interface ContributionPricingMeta {
  // 存取模式
  accessMode: "open" | "priced" | "collab_open" | "collab_gated" | "priced_collab";
  
  // 定價（accessMode 包含 priced 時）
  price?: number;  // DP 數量
  
  // 內容分層
  outlineBreak?: number;  // content 字串中的分割位置（字元數）
  // 如果 null，系統自動取前 280 字元或第一個段落
  
  // 合作門檻（accessMode 包含 collab 時）
  collaborationGate?: {
    minLevel?: number;           // 最低等級（1-6）
    minReputation?: number;      // 最低聲望分數
    requiredDisciplines?: string[]; // 要求的學科背景
    description?: string;        // 作者對合作夥伴的描述（「尋找統計分析專家」）
    seekingType: "academic" | "commercial" | "either";  // 合作性質
  };
}
```

## 四、購買 vs. 合作的機制設計

### 4.1 購買流程（Purchase）

```
買方看到 contribution → 讀大綱 → 點「Unlock for N DP」
  → 確認對話框：「This grants you read + cite access. No collaboration obligation.」
  → 扣除 DP（10% 平台 sink）→ 作者收到 90% DP
  → 細節立即解鎖 → 買方的 profile 中記錄「Purchased access」
  → 買方可在自己的 contribution 中引用，但必須標示來源
```

**購買後的權利：**
- ✅ 閱讀完整內容
- ✅ 在自己的 contribution 中引用（必須 @mention 原作者）
- ✅ 用於自己的研究
- ❌ 不能轉售或分享給他人
- ❌ 不能直接複製內容為自己的 contribution
- ❌ 沒有合作義務

### 4.2 合作流程（Collaboration）— Shopee/Amazon 級簡化

**【Product Designer 核心判斷】** 合作流程的靈感來自電商：Shopee 上「聯絡賣家」只需要一個按鈕 + 一行訊息，不是填 10 個欄位的申請表。DC 的合作申請應該同樣輕量——**一鍵發出興趣，讓後續對話自然展開**。

#### 買家視角（申請方）— 三步完成

```
Step 1: 看到有趣的 contribution → 點「🤝 Interested」按鈕
        ↓ 系統自動帶入你的 profile 摘要（等級、學科、公開 contributions 數）
        ↓ 一行選填訊息框：「Hi, I work on acoustic ecology and could contribute field data.」
        ↓ 合作類型快選：○ 🎓 Academic  ○ 💼 Commercial  ○ 🔬 Either
        
Step 2: 點「Send Request」→ Done. 
        ↓ 作者收到通知（像 Shopee 的「您有新訊息」）
        ↓ 如果需要押金（作者設定的），結帳時自動凍結，像購物車結帳

Step 3: 等回覆。狀態顯示在你的「My Requests」頁面：
        🟡 Pending → 🟢 Accepted → 🔓 Details Unlocked
                   → 🔴 Declined（押金自動退還）
```

#### 賣家視角（作者）— 訂單管理式

```
通知：「🤝 New collaboration request on your contribution」
       ├─ 申請者 profile 預覽（等級、學科、recent contributions）
       ├─ 一行訊息
       └─ [Accept] [Decline] [Chat First]
       
「Chat First」→ 開啟 1:1 對話（不解鎖細節），聊清楚再決定
「Accept」→ 細節立即解鎖，預設 Covenant 自動生效
「Decline」→ 押金退還，可附一行理由（選填）
```

#### 為什麼這樣設計比原版好

| 原版 | 簡化版 | 改善 |
|------|--------|------|
| 填寫完整申請表（自我介紹+能力+期望+...） | 系統自動帶入 profile + 一行選填訊息 | 申請 friction 從 5 分鐘降到 30 秒 |
| 押金必付 | 押金由作者決定是否要求；🏔 Trailblazer+ 免押金 | 低等級用戶也能輕鬆嘗試 |
| 填條款 → 雙方簽署 | 預設 Covenant 自動生效（接受 = 同意） | 消除法律文件恐懼 |
| 等審核才能對話 | 「Chat First」選項讓雙方先聊 | 類似 Shopee 的「聊聊」功能 |

### 4.3 合作條款（Collaboration Terms）

接受合作時自動生效的**預設 Covenant**（一句話版本顯示在 Accept 按鈕旁）：

> By accepting, both parties agree to DC's Collaboration Covenant: co-credit shared work, don't publish gated content independently, cite each other in derived works. [Full text →]

**完整條款：**
1. Shared contributions are co-credited (both parties in CreditV2)
2. Neither party may publish the gated content independently
3. Derived works cite both parties
4. Either party may exit — previously shared content remains accessible to both
5. Disputes go through DC community mediation

**合作類型標示：**

| 標示 | 含義 | 說明 |
|------|------|------|
| 🎓 Academic | 學術共著 / 共同發表 | 目標是合作產出 |
| 💼 Commercial | 技術授權 / 商業應用 | 購買後可商用，無合作義務 |
| 🔬 Either | 都可以談 | 讓雙方先聊再決定 |

### 4.4 Chat First — 技術設計與隱私保證

#### 資料模型（方案 A：JSON messages on CollaborationRequest）

```prisma
model CollaborationRequest {
  id              String   @id @default(uuid())
  applicantId     String   @map("applicant_id")
  contributionId  String   @map("contribution_id")
  status          String   @default("pending")
  // 狀態機: pending → chatting → accepted / declined / withdrawn
  //         pending → accepted / declined（跳過 chat 直接決定也可以）
  seekingType     String   @map("seeking_type")
  message         String                         // 初始申請訊息
  depositAmount   Int      @default(0) @map("deposit_amount")
  messages        Json     @default("[]")        // [{senderId, text, createdAt}]
  respondedAt     DateTime? @map("responded_at")
  completedAt     DateTime? @map("completed_at")
  createdAt       DateTime @default(now()) @map("created_at")
  updatedAt       DateTime @updatedAt @map("updated_at")
  
  @@index([contributionId])
  @@index([applicantId])
  @@map("collaboration_requests")
}
```

#### 隱私三層保證

**Layer 1: API 層面嚴格隔離**

```typescript
// POST /api/contributions/[id]/collab/[reqId]/message
// GET  /api/contributions/[id]/collab/[reqId]/messages

async function handler(req, res) {
  const session = await getSession();
  const request = await prisma.collaborationRequest.findUnique({
    where: { id: reqId },
    include: { contribution: { select: { authorId: true } } },
  });
  
  // ✅ 只有兩個人能存取：申請者 + 作者
  const isApplicant = session.user.id === request.applicantId;
  const isAuthor = session.user.id === request.contribution.authorId;
  if (!isApplicant && !isAuthor) {
    return res.status(403).json({ error: "Access denied" });
  }
  
  // ✅ messages 欄位只在這個 API 回傳，其他 API 永遠不 include
  // ✅ status 欄位對外只顯示計數，不顯示內容
}
```

**Layer 2: 前端隔離 — 其他人完全看不到 chat 的存在**

```
第三方看到的：
┌─────────────────────────────────────────┐
│  🤝 4 people interested · 2 chatting    │  ← 只有數字
│  [🤝 Interested]                        │  ← 自己的申請按鈕
└─────────────────────────────────────────┘

申請者自己看到的：
┌─────────────────────────────────────────┐
│  Your request: 💬 Chatting              │
│  [Open conversation]                    │  ← 進入自己的 chat
└─────────────────────────────────────────┘

作者看到的：
┌─────────────────────────────────────────┐
│  4 requests · 2 chatting · 1 accepted   │
│  [Manage requests]                      │  ← 進入管理面板
└─────────────────────────────────────────┘
```

**Layer 3: 訊息內容不進入任何公開索引**

- `messages` JSON 不被搜尋引擎索引
- 不出現在 thread 的 contribution 列表中
- 不計入任何公開統計（like 數、comment 數等）
- 作者刪除 request 時，messages 一併刪除（但 request 紀錄本身保留用於防抄襲審計）

#### Chat First 的狀態機

```
                    ┌──── declined ────┐
                    │                  ↓
pending ──→ chatting ──→ accepted ──→ completed
  │                        │
  │                        └──→ withdrawn (by applicant)
  │
  └──── accepted（作者跳過 chat 直接接受）
  └──── declined（作者跳過 chat 直接拒絕）
```

### 4.5 Reach Out 計數 — 社會證明與活躍度指標

像 Fiverr/Upwork 顯示「42 people contacted this seller」一樣，DC 在每個 gated contribution 和每個使用者的 profile 上顯示合作熱度。

#### Contribution 卡片上的顯示

```
┌──────────────────────────────────────────────────┐
│  [🔬 Data] [ecology] [🗺 Cartographer]  ·  3h    │
│                                                    │
│  A novel acoustic method for estimating canopy...  │
│  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │
│                                                    │
│  🤝 7 interested · 3 chatting · 1 collaborating   │
│  🔓 12 unlocked (purchased)                       │
│                                                    │
│  [🔓 Unlock 120 DP]  [🤝 Interested]             │
└──────────────────────────────────────────────────┘
```

**顯示規則：**

| 指標 | 可見對象 | 說明 |
|------|----------|------|
| `N interested` | 所有人 | 包含 pending + chatting + accepted，社會證明 |
| `N chatting` | 所有人 | 表示這個 contribution 有活躍對話 |
| `N collaborating` | 所有人 | 已接受的合作 |
| `N unlocked` | 所有人 | 購買次數，類似「已售 N 件」 |
| 具體是誰申請 | ❌ 只有作者看得到 | 隱私保護 |
| 申請訊息內容 | ❌ 只有雙方看得到 | 隱私保護 |

**Profile 指標說明：**

|------|----------|------|
| **Reach-outs received** | 歷史所有 CollaborationRequest 總數 | 受歡迎程度（像 LinkedIn 的 profile views） |

#### 查詢效能考量

**【Software Engineer】** 這些計數不需要每次都 `COUNT(*)`。用兩種策略：

1. **Contribution 層級的計數：** 在 `Contribution.metadata` 中快取 `{ interestedCount, chattingCount, collaboratingCount, purchaseCount }`，每次 request 狀態變更時更新。讀取時直接取 JSON，不需要 JOIN。

2. **Profile 層級的聚合：** 在 `PointsAccount` 上新增幾個快取欄位（`totalReachOuts`, `activeCollabs`, `totalSales`），背景 job 或 event-driven 更新。

這樣 contribution 卡片和 profile 頁面都是 O(1) 讀取，不需要每次 count。

### 4.6 防止「偷走構想」的機制

**【Devil's Advocate】** 這是整個系統最大的風險：有人透過合作申請窺探大綱內容，獲取足夠線索後就自己做，不走合作流程。

**多層防護設計：**

| 層 | 機制 | 說明 |
|----|------|------|
| L1 | **大綱必須足夠模糊** | 系統提供 guidelines：大綱應說明「做什麼」但不說「怎麼做」。例如「A novel method for 3D reconstruction from SEM images」而非描述具體演算法 |
| L2 | **SHA-256 時間戳** | 作者的完整內容早已 hash 過。即使有人看到大綱後「獨立發現」，原作者有時間證明 |
| L3 | **合作申請記錄** | 所有合作申請（包括被拒絕的）永久記錄在鏈上。如果申請後不合作卻發佈類似內容，社群可以看到時間線 |
| L4 | **合作保證金** | 申請合作需押 DP，提高惡意窺探的成本 |
| L5 | **舉報機制** | 類似學術不端舉報，加上平台記錄作為證據 |
| L6 | **最低公開要求** | 尋找合作者的 contribution 必須有一定的公開歷史（如：帳號 ≥ 30 天、至少 3 個公開 contributions）才能設定合作門檻 |

## 九、Devil's Advocate — 風險與反駁

### 「若我是你最強的反對者」

**1. 定價會毒化學術文化。**

學術界的核心價值是開放共享。一旦「最好的 insights 都藏在付費牆後面」，DC 就變成另一個 Elsevier——而這正是它聲稱要打倒的。

**對策：** 強制要求所有定價內容必須有公開大綱，且發佈公開內容本身就獲得 DP 獎勵。機制設計上確保「公開分享」不比「定價販售」虧——公開內容透過 likes、citations、collaboration requests 也能持續賺 DP。另外，Question 和 Replication 類型不建議定價（UI 提示）。

**2. 積分經濟很容易被 game。**

兩個帳號互相 like、互相買內容、互刷積分。這在 Stack Overflow 早期就是嚴重問題。

**對策：** (a) 同一帳號對同一 thread 的 like 獎勵每天上限 1 次；(b) 交易雙方的 IP/session 比對；(c) 新帳號前 30 天只能獲得 50% 的被動收入（likes）；(d) 月度被動收入上限；(e) 社群檢舉 + 管理員審查。

**3. 合作流程太重（friction 太高）。**

填申請表 → 等審核 → 押金 → 同意條款 → 才能看到內容。如果平台只有 50 個用戶，這流程會讓每次合作耗時數天，沒人會用。

**對策：** **MVP 要簡化。** 建議第一版的合作流程：(1) 申請只需一行訊息 + 自動帶入 profile；(2) 押金可以是 0（Level 3+ 免押金）；(3) 條款用預設值不需自訂。只有當平台大到需要防濫用時才啟用完整版。

**4. Outline 洩漏太多？洩漏太少？**

太多：等於白送。太少：沒人知道你在做什麼，找不到合作者。這個平衡點極難拿捏，而且因 discipline 而異（數學只需一行公式就洩漏核心，生態學可能需要一段描述才讓人理解方向）。

**對策：** 不試圖一刀切。讓作者自己決定 `outlineBreak` 的位置，提供 preview 讓他們看到「別人會看到什麼」。加上 discipline-specific guidelines（「物理學建議：只描述問題的現象學面向，不透露數學框架」）。

**5. 逆轉觸發條件：什麼時候應該砍掉這功能？**

- 如果上線 6 個月後 < 5% 的 contributions 使用定價功能 → 功能太複雜或需求不存在
- 如果 > 50% 的 contributions 定價但購買率 < 2% → 定價太高或信任不足
- 如果合作完成率 < 20%（大多申請被拒或中途退出）→ 合作機制 friction 太高

## 十、專家審查紀錄（v1.2 修訂依據）

> 以下為 Software Engineer、Product Designer、Devil's Advocate、Entrepreneur (Pragmatic) 四位專家的審查摘要，以及依據審查做出的設計修訂。

### 10.1 關鍵修訂一覽

| # | 來源 | 問題 | 修訂 |
|---|------|------|------|
| R1 | SE | `balance` 並發更新 race condition | 所有 balance 更新必須用 `UPDATE SET balance = balance + delta` 原子操作，包在 `$transaction` 中 |
| R2 | SE | Chat JSON 併發覆寫 | 用 Postgres `jsonb_concat` append 而非整欄覆寫；SQLite fallback 用 application-level lock |
| R3 | SE | `evaluateContributionAccess` 變 async 造成 N+1 | Thread page 預先批次載入該 user 的 purchases + collaborations 為 Set，傳入同步函式判斷 |
| R4 | SE | 計數快取一致性風險 | MVP 階段不做快取，直接 `COUNT(*)`；有效能問題再加 |
| R5 | PD | ContributionForm 認知爆炸 | 改成**情境模板**漸進揭露：「免費公開 / 付費解鎖 / 找合作者」三選一，選了才展開子選項 |
| R6 | PD | 新手看到模糊付費牆 = 壞印象 | 新手預設看 open 內容；priced 內容加上「為什麼收費」的一行解釋欄位 |
| R7 | PD | CSS blur 像騙錢 | 改成**摘要+鎖定**模式：outline 完整可讀（像 preprint abstract），details 顯示「🔒 N paragraphs · N figures locked」而非視覺模糊 |
| R8 | PD | 等級排序不直覺 | 等級名旁邊永遠並列 `Lv.N`，如 `🗺 Cartographer (Lv.3)` |
| R9 | PD | 合作流程太像購物 | Interested 按鈕保留但改名 `📝 Propose Collaboration`；申請需附 2-3 句合作意圖（必填），不只「一行選填」|
| R10 | DA | 冷啟動時社會證明數字反效果 | 計數 < 3 時隱藏具體數字，改顯示狀態標籤（「Open for collaboration」） |
| R11 | DA | Purchase 洗 Reputation 攻擊 | **Purchase 的 DP 不計入 Reputation**。Reputation 只來自：base earn（發佈）+ like/citation/review 被動收入 + CreditV2 加權 |
| R12 | DA | Commercial 合作 Covenant 無法律效力 | 💼 Commercial 類型強制導向外部 e-signature（DocuSign/HelloSign），Covenant 僅適用 🎓 Academic |
| R13 | DA | 先 open 後 priced = 免費引流後漲價 | **Grandfather clause**：轉 priced 前已 like/comment 的使用者保有永久免費存取權 |
| R14 | DA | Reviewer 被結構性低估 | Review/critique 的 DP 權重拉高至 +5（原 +3）；開放「Reviewer」為獨立升等路徑——純審查不發表也能升等 |
| R15 | Entrepreneur | 0 用戶蓋經濟系統 = 蓋機場 | **Phase 重新排序**（見下方）——Phase 0 先做用戶成長，Phase 1 才做最小積分 |

### 10.2 Reputation 公式修訂（R11）

```
Reputation = Lifetime DP Earned from:
               base publish rewards
             + likes received × 2
             + citations received × 10
             + reviews received × 5
             （❌ 不含 purchase 收入）
           + CreditV2 Total Weight × 50
           + Verification Bonus
```

## 十一、修訂後實作路徑（Phased Rollout v2）

> **核心轉變：** 「先有用戶再有經濟」。Phase 0 的重點是讓平台值得用，經濟系統是 Phase 1 以後的事。

### Phase 0: 用戶成長基礎（現在）

- [ ] UI/UX 優化（見 DC-UIUX 規劃——已部分完成）
- [ ] 移除 placeholder testimonials，改為即時統計
- [ ] 手動邀請 5-10 位 beta testers（Ping 的學術人脈）
- [ ] 確保核心流程順暢：建 thread → 發 contribution → CreditV2 正確累積
- [ ] 收集「使用者是否願意定價/付費」的質化回饋
- **觸發條件進入 Phase 1：** ≥ 20 活躍用戶 且 收到 ≥ 3 次「我想定價我的內容」或「我想找合作」的自然需求信號

### Phase 1: 最小積分系統（2 週）

- [ ] `PointsAccount` + `PointsTransaction` models（原子更新 balance）
- [ ] 積分賺取：contribution publish + like + review（三條核心規則）
- [ ] Level 計算 + profile 顯示（`🗺 Cartographer (Lv.3) · 847 DP`）
- [ ] Navbar DP 餘額
- [ ] `/points` 頁面（簡版：餘額 + 等級 + 最近交易）

### Phase 2: 內容定價（2-3 週）

- [ ] ContributionForm 加入情境模板（免費/付費/合作三選一），漸進揭露
- [ ] 「摘要+鎖定」呈現元件（非 CSS blur）
- [ ] `ContentPurchase` model + purchase API（$transaction 原子操作）
- [ ] evaluateContributionAccess 批次預載擴展（R3）
- [ ] 交易手續費 10% sink
- [ ] 動態調價 + grandfather clause（R13）
- [ ] 「為什麼收費」一行解釋欄位（R6）
- [ ] 低計數時隱藏數字（R10）

### Phase 3: 合作機制（2-3 週）

- [ ] `CollaborationRequest` model（含 messages JSON + jsonb append）
- [ ] 「📝 Propose Collaboration」流程（附合作意圖必填）
- [ ] Chat First（API 隱私三層保證）
- [ ] Accept / Decline / Chat First 狀態機
- [ ] Reach-out 計數 + profile 指標
- [ ] Covenant（🎓 Academic 自動生效；💼 Commercial 導向外部 e-signature）

### Phase 4: 進階功能（需求驅動）

- [ ] Badge 成就系統
- [ ] Leaderboard
- [ ] Thread Boost
- [ ] 引用追蹤（@mention）

### Phase 5: 真實貨幣掛鉤評估（遠期，依用戶量決定）

**前提條件：** 平台活躍用戶 ≥ 500 且 DP 經濟已穩定運行 ≥ 6 個月。在此之前 DP 就是遊戲幣，不涉及任何金融概念。

## 附錄 A：與現有 DC 功能的交互矩陣

| 現有功能 | 與新系統的關係 |
|----------|---------------|
| Seal & Reveal | **共存不衝突**。sealed content 不能定價（因為內容隱藏中）。reveal 後可以選擇 open 或 priced |
| Graduated Visibility | **延伸**。accessMode 是 visibility 之上的第二層。一個 contribution 必須先是 "public" 或 "shared"，然後才能設定 priced/collab |
| CreditV2（學術歸因） | **平行系統**。DP 交易不影響 CreditV2 歸因。購買他人 contribution 不會讓你獲得 CreditV2（只有 DP 轉帳） |
| Trust Level | **互補**。Level 是自動計算的聲望；Trust Level 是管理員控制的權限。取嚴格者 |
| AI Review | **不受影響**。AI review 不涉及 DP |
| Replication | **加分項**。成功 replication 給原作者 + 複製者都獎勵 DP |

## 附錄 B：參考平台機制比較

| 平台 | 貨幣 | 賺取 | 消費 | 等級 | 定價 |
|------|------|------|------|------|------|
| Stack Overflow | Reputation | 回答被採納/upvote | Bounties | 權限閾值 | 無 |
| ResearchHub | RSC (ERC-20 token) | 發論文、評論、curate | 打賞、bounties | 基於 RSC 持有量 | 無直接定價 |
| Kaggle | Points + Medals | 比賽、notebooks、discussions | 無消費用途 | Novice → Grandmaster | 無 |
| Patreon (研究) | USD | 訂閱者付費 | 創作者收入 | 無 | 月費訂閱 |
| **DC（本設計）** | **DP** | **貢獻、互動、被購買** | **購買內容、合作押金、boost** | **6 級 reputation-based** | **單篇定價 + 合作門檻** |

DC 的獨特定位：**單篇粒度的知識定價 + 學術合作配對**，不是 Stack Overflow 的純聲望系統，也不是 Patreon 的訂閱制，而是更接近「學術知識的小額交易市場」。
